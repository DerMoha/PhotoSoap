Deepen the photo review lifecycle

Files

  • PhotoSoap/ViewModels/PhotoReviewViewModel.swift
  • PhotoSoap/Views/PhotoReviewView.swift
  • PhotoSoap/Views/Components/DeleteQueueSheet.swift
  • PhotoSoap/Views/Components/DeleteQueueTray.swift
  • PhotoSoap/Views/Components/DeleteBatchExplainerSheet.swift
  • PhotoSoap/Utilities/UserDefaultsKeys.swift

Problem

The photo review Module is shallow: the Interface exposes delete queue state, persistence facts, rollback ordering, toast flags, haptics timing, and Photos recovery rules that belong inside one Implementation.

Solution

Deepen the photo review lifecycle so queue, commit, rollback, restore, and prune behavior sit behind one Seam, while SwiftUI only observes review outcomes.

Benefits

  • Locality: queue bugs concentrate in one Module.
  • Leverage: one Interface covers queue, commit, rollback, restore, and prune.
  • Tests: deletion queue lifecycle can run without SwiftUI gesture state.
  • Deletion test: deleting the queue code today spreads complexity across review view, stats, Photos access, and persistence.

Hide Photos behind a deeper Photo Library Adapter

Files

  • PhotoSoap/Models/Photo.swift

Problem

The Photo Library Module has a broad Interface: authorization, albums, filters, thumbnails, video previews, deletion, UIKit settings, and raw Photos types leak across the Seam.

Solution

Deepen the Photo Library Adapter so Photos framework details stay inside the Implementation and review modules see library facts, media previews, and deletion outcomes.

Benefits

  • Locality: Photos churn stays inside one Adapter.
  • Leverage: review, filter, preview, and stats callers stop learning Photos invariants.
  • Tests: sequencing, limited access, missing assets, and filter exhaustion become deterministic.
  • Deletion test: deleting Photos-specific code today breaks most app-facing modules because the Interface is Photos-shaped.

Problem

Review accounting is shallow because callers must know the ordering: queued delete counts as reviewed now, delete count and storage freed happen later, and rollback must remove history plus achievement state.

Solution

Move review accounting transitions behind one Seam so counters, challenges, achievements, review history, and rollback invariants live in one Implementation.

Benefits

  • Leverage: callers stop sequencing low-level stats mutations.
  • Tests: behavior checks replace manual call choreography.
  • Deletion test: removing view model snapshots today allows inconsistent stats after failed deletion.

Problem

Privacy collection is shallow: two modules share one defaults key, settings toggles both, and review callers choose between event tracking and aggregate metrics.

Solution

Deepen the privacy collection Module so opt-in state, event recording, aggregate buckets, install registration, and flush timing sit behind one policy Seam.

Benefits

  • Leverage: one opt-in decision controls all collection behavior.
  • Tests: disabled collection, pending buckets, and flush retry behavior share one Interface.
  • Deletion test: deleting either current module leaves preference logic and review call sites behind.

Problem

Review feedback is shallow: many published flags, timers, haptics calls, celebration banners, warning toasts, and swipe-threshold effects sit beside domain review logic.

Solution

Deepen feedback timing only if it keeps growing: concentrate review feedback decisions behind a Seam while leaving HapticsService as the concrete Adapter.

Benefits

  • Locality: feedback timing bugs stop scattering across view state.
  • Leverage: one Module can drive haptics, toast, and banner outcomes.
  • Tests: threshold feedback and cancellation warning rules become observable without gesture rendering.
  • Deletion test: removing feedback code today leaves many flags and view branches behind, but core review still works.

Top recommendation

Start with the photo review lifecycle.

It has the strongest Locality and Leverage payoff: delete queue rules, persistence, rollback, pruning, and UI-facing state currently form one shallow Interface, and the deletion test shows the complexity reappearing across several callers. Deepening this Module creates the best test surface before touching the Photos Adapter or review accounting shape.
